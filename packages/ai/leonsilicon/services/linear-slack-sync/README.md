# @-/ai.leonsilicon.services.linear-slack-sync

Keeps one Slack channel per Linear issue, and one per Linear project. Leon works in Slack while his agents collaborate in Linear, so he follows their work through these channels. Each issue channel sits in the sidebar section named exactly after its issue's status, so the sidebar shows at a glance what is blocked on him and what is waiting on someone else. Issue comments are mirrored both ways. Since 2026-11-21 [autolinear](../autolinear/README.md) gives each of Leon's Slack messages an issue and channel at once, and this sync takes the channel over. Project channels belong to Linear's own Slack app, which posts project updates and project comments there and syncs their threads; this sync only makes sure every open project has one. It runs as a Cloudflare Worker; deployment is in [`apps/linear-slack-sync`](../../../../../apps/linear-slack-sync/README.md).

**Ignored:** bot posts (including Composio, and Hermes's own except for a ping to Leon), system messages, and posts made as Leon with the slack-as-leon marker (`client_msg_id` starting `de1e6a7e`): Hermes's through slack-as-leon, and autolinear's copies of Leon's messages in new issue channels.

**No echoes:**

- A comment made from Slack is created with an ID derived from the Slack message (`stableUuid`), and that ID is recorded first. Linear's webhook for it is then recognized and skipped.
- A retried Slack event reuses the same ID.

## Issue channel topics

Linear Sync writes issue metadata to the Slack channel topic. The Slack bridge exposes it as the Matrix room topic that [Leon for Zami](https://github.com/leonsilicon/zami-plugin-leon) reads. The topic starts with the status name for older plugin versions and uses this format for compact issue rows:

```text
Awaiting Leon · linear:v1 started #f2c94c p2 · https://linear.app/leonsilicon/issue/LEON-381 · Cancel club Fongo Works phone service
```

The workflow field carries the Linear state type and hex color (`-` when unavailable), followed by `p0` through `p4` for no priority, urgent, high, medium, and low. When it fits, the field also includes the title's metadata as a JSON object after the priority, with literal middle dots escaped. The title comes last and may contain middle dots. Slack limits topics to 250 characters, so long titles are shortened and oversized optional metadata stays in Linear. The daily tick rewrites old topics for open issues and picks up workflow color and priority changes without posting a status message.

## Title metadata

Leon's rule (2026-11-18) is that status data ends the title as a YAML 1.2 flow mapping in backticks:

```
switch to rogers `{event: Rogers unlimited BYOD deal, stop: 2026-12-01}`
```

- Values containing `, : { } [ ] #` are double-quoted.
- A bare date `YYYY-MM-DD` means midnight in Toronto. Times are RFC 3339 with an offset.
- `start` (Awaiting Date) and `event` and `stop` (Awaiting Listener) belong to their status and are removed when the issue leaves it. `due` belongs to the issue and stays.
- `parseTitle` and `formatTitle` read and write the mapping, and `metaInstant` turns a value into an instant.

## autolinear's issues

[autolinear](../autolinear/README.md) makes each of Leon's Slack messages an issue (Leon's rule, 2026-11-21) and opens its channel itself, as Leon, so the issue and channel appear at once. This sync then takes the channel over, off autolinear's path:

- **Hand-over (`Sync.adopt`).** autolinear calls Linear Sync's Durable Object directly (`/adopt`, through a binding with `script_name: "linear-slack-sync"`; the public Worker doesn't route it) as soon as the channel exists. It invites the bot and Hermes in one call, records the channel, and queues an `adopted` job. Repeating it does nothing.
- **The rest (`adopted` job).** Files the issue in the project whose channel Leon wrote in (`projectByChannel`), quotes a reply's thread's first message in the description, posts the intro (`From Leon's message in <link|a DM with Hermes>.`, pinging no one), then sets the topic and Awaiting Init section like any sync.
- **No second channel.** autolinear's issue IDs start with `a7011ea7` (`AUTOLINEAR_ID_PREFIX`). When the issue's own webhook comes before the hand-over, `syncIssue` leaves the issue alone and looks again two minutes later (`ADOPT_WAIT_MS`); by then the channel is recorded, or, if autolinear failed before handing it over, the issue gets a channel the usual way, adopting autolinear's by its number when it exists.

From then on it's an ordinary issue channel: when Hermes has answered the copy of Leon's message, a ping to him leaves the issue in Awaiting Leon, and an answer without one closes it as Done.

## Times

Nothing polls for times. Linear sends no webhook when a time arrives (checked 2026-11-19: SLA webhooks need its Business plan, and an SLA replaces the due date; a reminder set by an app reaches the app's inbox on time but not its webhook; due-date notifications go out once per issue, on Linear's hourly run), so each time is a timer in the sync's own queue:

- Every open issue has at most one timer, set for the earliest of its times still to act on: the `start` of an Awaiting Date issue, the `stop` of an Awaiting Listener one, and a due time not yet announced. `syncIssue` sets it whenever the issue changes, so a webhook that changes a time, the status or the title moves or clears it. A time already past goes off at once.
- A timer is a delayed job in the queue, ID `timer:<issue id>@<ms>` (`Store.setTimer`). The Durable Object's alarm is always set for the earliest job, so it wakes the Worker on time, to the second. When it goes off, the sync reads the issue again and acts only on what is still true, so a stale timer does nothing.
- The daily tick is the safety net for a lost timer or a missed webhook.

### Due dates

Linear's own due date is a day with no time, so a time goes in the title: `due: 2026-12-01T17:00:00-05:00`, or a bare date for midnight.

- When the title has `due`, the sync sets Linear's due date to its day in Toronto, so Linear shows it, sorts by it and marks it overdue. If Linear's date is what changed (the date picker, or clearing it), the title follows instead: the same time of day on the new day, or no `due` once the date is cleared. Which changed comes from the webhook's `updatedFrom`.
- Without `due`, Linear's own due date counts, at midnight starting that day.
- When the time comes, the sync posts in `#feed-linear` (`LINEAR_FEED_CHANNEL`): `:date: Due: LEON-401: Send the invoice · due Tue, Dec 1, 5:00 PM · Awaiting Leon · #leon-401-…`, or "Overdue" when it posts more than an hour late (an issue first seen past its due time). It mentions no one.
- Each due time is announced once (the `fired` table keeps `due:<issue id>:<ms>`). A new due time is announced again.
- `#feed-linear` is created the first time it's needed (or by the daily tick): public, made by the Linear Sync bot, with Leon and Hermes in it. An archived one is unarchived.

## Sidebar sections

Slack has no public API for a person's sidebar. `Sidebar` uses the web client's own methods with Leon's web session (`xoxc-` token plus `d` cookie), the same kind slack-as-leon holds:

- `users.channelSections.list` returns sections as a linked list through `next_channel_section_id`.
- `users.channelSections.create` needs `name` and `emoji` (`""` is fine). `next_channel_section_id` places the new section before that one.
- `users.channelSections.channels.bulkUpdate` takes `insert` and/or `remove`, each a JSON array of `{channel_section_id, channel_ids}`.
- `users.channelSections.delete`.

Sections are created only when a channel needs them, in `SECTION_ORDER`, as one block at the top. A status missing from the order gets its section after the block. Without the session, everything else still works and sections are skipped.

## Project channels

Linear connects a project to a Slack channel natively ("Project channels" in Linear → Settings → Integrations → Slack, turned on 2026-11-19 with "Automatically create channel for new projects" and prefix `project-`). Linear's Slack app must stay installed in the workspace: the 2026-11-19 app cleanup uninstalled it, and no project got a channel until it was reconnected the same day. `/healthz` now reports `projects` so that shows up. The connected channel gets the project's updates, with each update's Slack thread synced both ways, and top-level project comments. Its ID is the project's `slackChannelId`.

Linear's public schema has no way to give an existing project such a channel without an OAuth consent per project. Linear's own app uses `projectCreateSlackChannel(id, slackChannelName, integrationId)`, which is left out of the published schema but accepts a personal API key. `LinearClient.createProjectChannel` calls it. Linear's bot then creates the public channel, invites the project's members, sets the topic to the project summary, and fills in `slackChannelId` within seconds. Linear switches the project's updates and comments on (`integrationsSettings`) by default.

- The integration and prefix come from Linear (`organization.slackProjectChannelIntegration`, `slackProjectChannelPrefix`). Without them, no channel is requested.
- A taken name gets `-2`, `-3`… A channel that still hasn't appeared is requested again after 30 minutes, not before.
- The sync's own bot doesn't join project channels. Leon's session joins him and invites Hermes, and archives and unarchives.
- Linear Sync appends `[linear-project:v1 #e99b51]` to the channel topic for Zami, with the project icon identifier after the color when set. It preserves the Slack summary and only appends metadata that fits the topic limit. Project webhooks and the daily tick refresh it, including for open day projects.
- Messages in a project channel aren't mirrored by this sync: Linear syncs its own threads.

## Day projects

A day's project (a project named after a date, `20261122` or `2026-11-22`; `projectDay` reads it) belongs to [dailylinear](../dailylinear/README.md) since 2026-11-21. It makes the project at midnight in Toronto, asks Linear's Slack app for its channel named `project-YYYY-MM-DD` at once, keeps the day's channel in Leon's Starred section, and marks each past day's project Completed and archives its channel. This sync, which did the channel part from 2026-11-19 (and Grok Bot's midnight routine the project), now only:

- never asks for a day's channel, and never files one in a section or stars or renames it;
- makes sure Leon and Hermes are in a day's channel and adds its icon metadata, as for any project;
- archives the channel when the day's project closes or is deleted, and unarchives it if it reopens.

`projectChannelName` still gives a day's project `project-YYYY-MM-DD`, which is the name dailylinear asks for.

## API

- `Sync`: `adopt(adoption)` for autolinear's hand-over (see [autolinear's issues](#autolinears-issues)), and `run(kind, payload)` for the jobs `linear` (a webhook body: Issue, Comment or Project), `adopted` (the rest of a hand-over), `answered` (Hermes's finished turn, judged), `slack` (a message, Hermes's ping to Leon included, or a ✅ or ❌ `reaction_added` event), `project` (a delayed look at a new project), `timer` (an issue's time came), `tick` and `backfill`, plus `syncIssue(issue, "live" | "quiet")` and `syncProject(project)`.
- `Store`: issue ↔ channel, project ↔ channel and comment ↔ message mappings, a Slack user name cache, and the durable job queue (dedupe for 3 days, backoff, `dead` after six attempts, optional delay), whose delayed jobs are also the timers (`setTimer`, `timer`), plus the `fired` record of due times announced. It runs over any `Sql`: a Durable Object's `storage.sql`, or `node:sqlite` in tests.
- `LinearClient`: Linear's GraphQL API with a personal API key, including `createProjectChannel` above, `team` and `createIssue` (with an ID the caller picks) for autolinear, and `projectsNamed`, `projectStatuses`, `createProject` (with an ID the caller picks) and `updateProject` for dailylinear.
- `botClient`: the Slack Web API with a bot token. `Sidebar` covers the sections above, and `tolerate` treats the listed Slack errors as success.
- `verifySlack` and `verifyLinear`: request signatures with a five-minute window.
- autolinear's IDs: `AUTOLINEAR_ID_PREFIX`, `autolinearIssueId`, `isAutolinearIssue`.
- Format helpers: `linearToSlack`, `slackToLinear`, `intakeTitle`, `excerptQuote` (from `#sync`), `channelName`, `projectChannelName`, `projectDay`, `localDay`, `channelNumber` and `channelTopic`, and for times `metaInstant`, `hasTime`, `zonedIso` (RFC 3339 in Toronto's offset), `withDay` (a time moved to another day), `addDays` and `localLabel`.
- `loadConfig(env)`: settings from the Worker's vars (the `#linear-slack-sync` items of the root `.env.schema`). `SLACK_LEON_USER_ID` and `SLACK_HERMES_USER_ID` are required: they have no built-in default.
