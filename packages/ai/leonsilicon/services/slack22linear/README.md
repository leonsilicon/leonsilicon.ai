# @-/ai.leonsilicon.services.slack22linear

The `22` in slack22linear stands for two-way sync between Slack and Linear.

Keeps one Slack channel per Linear issue, and one per Linear project. Leon works in Slack while his agents collaborate in Linear, so he follows their work through these channels. Each issue channel sits in the sidebar section named exactly after its issue's status, so the sidebar shows at a glance what is blocked on him and what is waiting on someone else. Issue comments are mirrored both ways. Since 2026-11-21 [autolinear](../autolinear/README.md) gives each of Leon's Slack messages an issue and channel at once, and this sync takes the channel over. Project channels belong to Linear's own Slack app, which posts project updates and project comments there and syncs their threads; this sync only makes sure every open project has one. It runs as a Cloudflare Worker; deployment is in [`apps/slack22linear`](../../../../../apps/slack22linear/README.md).

**Ignored:** bot posts (including Composio, and Hermes's own except for a command to Autolinear), system messages, and posts made as Leon with the slack-as-leon marker (`client_msg_id` starting `de1e6a7e`): Hermes's through slack-as-leon, and autolinear's copies of Leon's messages in new issue channels.

When Hermes's 👀 automatically moves an issue to Executing, AutoLinear adds ⚙️ to the same message, including a reply inside a thread. Successful commands from Hermes update the issue silently. When Executing expires, AutoLinear adds 👤 for Awaiting Leon to the message that set the lease. Status changes from Linear, Leon's slash command, and timers without a source message are posted in the issue channel.

**No echoes:**

- A comment made from Slack is created with an ID derived from the Slack message (`stableUuid`), and that ID is recorded first. Linear's webhook for it is then recognized and skipped.
- A retried Slack event reuses the same ID.

## Matrix metadata for Zami

The sync stores a full record per mapped Slack issue channel with its status, title, priority, URL, due date and workflow details. A protected, read-only endpoint serves the current records to the Beeper inbox. The publisher matches the Slack workspace and channel to a joined Matrix room and writes `ai.leonsilicon.linear.issue` as room account data. Closed issues keep their final status and deleted issues get a deletion marker.

The publisher writes project colors and icons as `ai.leonsilicon.linear.project` room account data. Zami displays issue details and project appearance as soon as their room account data arrives.

## Workflow details

Each issue keeps its title and Slack channel name. Create a new Linear issue for new work and link it to the original if related. The sync opens a separate Slack channel for it.

AutoLinear writes workflow details in the **AutoLinear workflow** section of the Linear description. Existing issues can still supply defaults from the old `[AWAITING: …]` prefix and backticked YAML at the end of the title:

```
switch to rogers `{event: Rogers unlimited BYOD deal, stop: 2026-12-01}`
```

- A bare date `YYYY-MM-DD` means midnight in Toronto. Times are RFC 3339 with an offset.
- `start` belongs to Awaiting Date. `who`, `event` and `stop` belong to Awaiting Trigger. `due` belongs to the issue.

## autolinear's issues

[autolinear](../autolinear/README.md) makes each of Leon's Slack messages an issue (Leon's rule, 2026-11-21) and opens its channel itself, as Leon, so the issue and channel appear at once. This sync then takes the channel over, off autolinear's path:

- **Hand-over (`Sync.adopt`).** autolinear calls slack22linear's Durable Object directly (`/adopt`, through a binding with `script_name: "linear-slack-sync"`; the public Worker doesn't route it) as soon as the channel exists. It invites the bot and Hermes in one call, records the channel, and queues an `adopted` job. Repeating it does nothing.
- **The rest (`adopted` job).** Files the issue in the project whose channel Leon wrote in (`projectByChannel`), quotes a reply's thread's first message in the description, then records the issue metadata and sets the Awaiting Init section like any sync.
- **No second channel.** autolinear's issue IDs start with `a7011ea7` (`AUTOLINEAR_ID_PREFIX`). When the issue's own webhook comes before the hand-over, `syncIssue` leaves the issue alone and looks again two minutes later (`ADOPT_WAIT_MS`); by then the channel is recorded, or, if autolinear failed before handing it over, the issue gets a channel the usual way, adopting autolinear's by its number when it exists.

The copy of Leon's message includes a footer that links to the source and the Linear issue. From then on it's an ordinary issue channel: Hermes's 👀 on the copy of Leon's message moves the issue to Executing, and Hermes's turn ends with a command to Autolinear that says where the issue goes.

## Autolinear's commands

Leon's rule (2026-11-23): Hermes ends every turn in an issue channel with one line that tells Autolinear, the autolinear Slack app's bot, what to do with the channel, and nothing moves on Hermes's answer otherwise. Before then, slack22linear judged the answer itself: a ping to Leon moved the issue to Awaiting Leon, and an answer without one closed it as Done, even an answer to his "thanks".

Slack runs slash commands only for people, so Hermes writes the command as a mention of Autolinear's bot at the start of a line. Leon can type the same words after `/autolinear`, which the [autolinear Worker](../../../../../apps/autolinear/README.md) hands to this queue.

```text
@Autolinear move done
@Autolinear move leon
@Autolinear move trigger --who "Apple App Review"
@Autolinear move trigger --event "Rogers BYOD deal" --stop 2026-12-01
@Autolinear move date --start 2026-12-01T09:00:00-05:00
@Autolinear move executing --until 2h
@Autolinear stay
@Autolinear help
```

- **Reading it (`#command`).** `commandLine` finds the last line that starts with the mention using Slack's `<@U…>` token or plain `@Autolinear`. A mention inside a line, a quote or a code block isn't a command. `parseCommand` uses Citty for the status and options. Use `--option value` or `--option=value` after the status and quote values with spaces. Slack's curly double quotes work too. Existing `key=value` commands and `help` still work. `--help` and `-h` show the command guide. Status names are case-insensitive and accept the "Awaiting " prefix. Set Awaiting Hermes directly in Linear.
- **When.** A Hermes message with a command line marks the turn as having said what to do at once. The command itself runs `COMMAND_SETTLE_MS` (3 s) after Hermes last posted or edited the message, from its newest text, so a reply streamed by editing is read whole. Each ordinary reply acts once. In a task's parent message, only each new full Hermes answer can run a command. The quick answer, agent reports and Hermes's in-thread progress notes are informational.
- **What `move` does.** It updates the status and workflow details in one Linear update and syncs the channel. Hermes can mention Leon in that message when his attention is needed. Awaiting Date needs `--start`. Awaiting Trigger accepts `--who` for an external response, or `--event` and `--stop` for a timed event. Switching between the two clears the previous wait's details. Values can come from the command or the issue's existing workflow details. Hermes's 👀 keeps those values so it can move the issue back afterwards. The older `move others` and `move listener` commands also resolve to Awaiting Trigger.
- **Delegation.** Hermes chooses agents based on the task and uses `move executing --until <when it should be done>` while a delegated agent works: a duration (`45m`, `2h`, `1h30m`) or a time, at most 24 hours away (`MAX_LEASE_MS`). Without `--until` it holds for an hour (`EXECUTING_MS`). `--until` goes with Executing only. A move to Awaiting Hermes in Linear pings Hermes to pick up the issue and decide how to proceed.
- **`stay`.** Keeps the status. In Executing, where Hermes's 👀 put the issue, Hermes's `stay` means the status from before the 👀 (`acks`), such as Awaiting Leon or Awaiting Trigger. When there was none to go back to (a new issue in Awaiting Init, Awaiting Hermes, or Executing already), Autolinear refuses it and asks Hermes to say who is next or which agent is still working. Leon's `/autolinear stay` keeps the status as it is.
- **Answers.** Successful Hermes commands run silently. When a command fails, AutoLinear explains why in the thread and mentions Hermes. Leon's `/autolinear` gets its answer privately through Slack's response URL.
- **Reminders.** See the table above. Autolinear's bot is invited to every issue channel with Hermes. In an older channel it isn't in yet, Leon's session invites it the first time it posts. Hermes answers its mentions because Hermes's `SLACK_ALLOWED_USERS` lists it, alongside `allow_bots: mentions`.

### Executing is a lease

Leon's rule (2026-11-25): nothing may sit in Executing with no one working on it. Before this, Executing was a label that Hermes's 👀 or `move executing` set and nothing had to clear, and LEON-479 to 498 sat there for up to 30 hours: a Codex handoff that failed before Hermes's turn started (no ✅, so no reminder), `stay` answered to a reminder (which kept the 👀's Executing), and `move executing` for agents whose reports nobody acted on.

Now every issue in Executing has an end time (timer `lease:<issue>`), and when it comes the issue goes to Awaiting Leon (`onLeaseEnded`). Signs of work push the end to at least 15 minutes from now (`LEASE_MS`): Hermes's gateway reporting a turn running in the channel (job `turns`, about every minute), Hermes's 👀, and any post or edit in the channel other than Autolinear's and slack22linear's own, such as Task progress updates and agents' reports. `move executing --until` sets the end exactly. AutoLinear reacts to Hermes's command message when the lease expires, or to the message Hermes took up with 👀 if that started the lease. Later work can extend the deadline and the reaction still goes on the source message. The explanation stays in Linear when there is a message to react to. An issue that enters Executing any other way, such as a move in Linear, gets 15 minutes and a channel notice at expiry. The daily tick gives a lease to any Executing issue without one. The issue keeps its workflow details, so Leon or Hermes can send it back to a wait it had. Logs: `lease_ended`.

## Routine and Watcher projects

Leon's rule (2026-11-25): what repeats and what keeps watching are projects, each in a project status of its own, never issues left open.

- **Routine** (the project status that was Backlog until then): one of Leon's routines, scheduled in Muse. The project's body starts with a line `Muse routine: <id>` (the ID Muse's `tasks.list` gives), and work about the routine goes in the project. Due runs appear in `#feed-muse` for the Watcher that holds Hermes's work instructions.
- **Watcher**: a standing watch. Its summary says what to watch for in the `#feed-*` channels and its body what to do with each case. [Autotrigger](../autotrigger/README.md#watchers) opens an Awaiting Hermes issue in it for each new case and sends follow-ups to that issue. The project stays open.

The [hermes22muse](../../../../../apps/hermes-plugin-leon/hermes22muse/README.md#reminders-and-routines) relay on Hermes Cloud reads Muse's scheduled tasks every ten minutes and sends them through [autolinear's Worker](../../../../../apps/autolinear/README.md) to this queue (job `routines`). `Routines` (`#routines`) then keeps the Routine projects in step:

- A routine (a repeating schedule, not Muse's heartbeat or a one-time reminder) that Muse runs and no Routine project links to gets a project: named after it, in Routine, with the link line, its schedule (`daily@08:00 (America/Toronto)`) and its file in Muse's workspace. Its ID comes from the routine, so it's made once. An unlinked Routine project with the routine's name gets the link instead. slack22linear then gives it a channel like any project. A paused routine without a project gets none.
- What needs judgment becomes an issue in **Awaiting Hermes**, filed in the project, asked once: a Routine project with no link line ("Link Taxes to its Muse routine"); a link to a routine Muse no longer has, after 20 minutes missing (`ROUTINE_MISSING_GRACE_MS`; one Muse can't read for the moment isn't missing); a routine still running whose project left Routine or was deleted. Hermes asks Leon, then links it, has Muse make or stop the routine, or moves the project.
- A day's project is never a routine. A snapshot older than 30 minutes, older than the last one, or empty (Muse always lists its heartbeat) changes nothing.

The table `routine_state` remembers each project's link (so a closed project still names its routine), how long a routine has been missing, and what was asked.

## Times

Nothing polls for times. Linear sends no webhook when a time arrives (checked 2026-11-19: SLA webhooks need its Business plan, and an SLA replaces the due date; a reminder set by an app reaches the app's inbox on time but not its webhook; due-date notifications go out once per issue, on Linear's hourly run), so each time is a timer in the sync's own queue:

- Every open issue has at most one timer, set for the earliest of its times still to act on: the `start` of an Awaiting Date issue, the `stop` of an Awaiting Trigger issue, and a due time not yet announced. `syncIssue` sets it whenever the issue changes, so a webhook that changes a time or status moves or clears it. A time already past goes off at once.
- A timer is a delayed job in the queue, ID `timer:<issue id>@<ms>` (`Store.setTimer`). The Durable Object's alarm is always set for the earliest job, so it wakes the Worker on time, to the second. When it goes off, the sync reads the issue again and acts only on what is still true, so a stale timer does nothing.
- The daily tick is the safety net for a lost timer or a missed webhook.

### Due dates

Linear's own due date is a day with no time, so AutoLinear keeps the time in the workflow details: `due: 2026-12-01T17:00:00-05:00`, or a bare date for midnight.

- When the workflow has `due`, the sync sets Linear's due date to its day in Toronto. Changing the date in Linear moves the workflow's due time to the same time of day on the new date. Clearing the date clears the workflow's due time.
- Without `due`, Linear's own due date counts, at midnight starting that day.
- When the time comes, the sync posts in `#feed-linear` (`LINEAR_FEED_CHANNEL`): `:date: Due: LEON-401: Send the invoice · due Tue, Dec 1, 5:00 PM · Awaiting Leon · #leon-401-…`, or "Overdue" when it posts more than an hour late (an issue first seen past its due time). It mentions no one.
- Each due time is announced once (the `fired` table keeps `due:<issue id>:<ms>`). A new due time is announced again.
- `#feed-linear` is created the first time it's needed (or by the daily tick): public, made by the slack22linear bot, with Leon and Hermes in it. An archived one is unarchived.

## Sidebar sections

Slack has no public API for a person's sidebar. `Sidebar` uses the web client's own methods with Leon's web session (`xoxc-` token plus `d` cookie), the same kind slack-as-leon holds:

- `users.channelSections.list` returns sections as a linked list through `next_channel_section_id`.
- `users.channelSections.create` needs `name` and `emoji` (`""` is fine). `next_channel_section_id` places the new section before that one.
- `users.channelSections.channels.bulkUpdate` takes `insert` and/or `remove`, each a JSON array of `{channel_section_id, channel_ids}`.
- `users.channelSections.delete`.

Sections are created only when a channel needs them, in `SECTION_ORDER`, as one block at the top. A status missing from the order gets its section after the block. Without the session, everything else still works and sections are skipped.

## Project channels

Linear connects a project to a Slack channel natively ("Project channels" in Linear → Settings → Integrations → Slack, turned on 2026-11-19 with "Automatically create channel for new projects" and prefix `project-`). Linear's Slack app must stay installed in the workspace: the 2026-11-19 app cleanup uninstalled it, and no project got a channel until it was reconnected the same day. `/healthz` now reports `projects` so that shows up. The connected channel gets the project's updates, with each update's Slack thread synced both ways, and top-level project comments. Its ID is the project's `slackChannelId`.

Linear's public schema has no way to give an existing project such a channel without an OAuth consent per project. Linear's own app uses `projectCreateSlackChannel(id, slackChannelName, integrationId)`, which is left out of the published schema but accepts a personal API key. `LinearClient.createProjectChannel` calls it. Linear's bot then creates the public channel, invites the project's members, sets the topic to the project summary, and fills in `slackChannelId` within seconds. Linear switches the project's updates and comments on (`integrationsSettings`) by default.

- The integration and prefix come from Linear (`organization.slackProjectChannelIntegration`, `slackProjectChannelPrefix`). Without them, no channel is requested.
- A taken name gets `-2`, `-3`… A channel that still hasn't appeared is requested again after 30 minutes, not before.
- The sync's own bot doesn't join project channels. Leon's session joins him and invites Hermes, and archives and unarchives.
- Project webhooks and the daily tick record colors and icons for the Matrix publisher, including for open day projects. Slack topics are available for project summaries.
- The Beeper inbox publishes closed project channel IDs as Matrix account data for Zami. The list combines Slack archives with archived, completed, and canceled Linear projects. Project webhooks, the daily tick, backfills, and Slack archive events refresh it.
- Messages in a project channel aren't mirrored by this sync: Linear syncs its own threads.

## Day projects

A day's project (a project named after a date, `20261122` or `2026-11-22`; `projectDay` reads it) belongs to [dailylinear](../dailylinear/README.md) since 2026-11-21. It makes the project at midnight in Toronto, asks Linear's Slack app for its channel named `project-YYYY-MM-DD` at once, keeps the day's channel in Leon's Starred section, and marks each past day's project Completed and archives its channel. This sync, which did the channel part from 2026-11-19 (and Grok Bot's midnight routine the project), now only:

- never asks for a day's channel, and never files one in a section or stars or renames it;
- makes sure Leon and Hermes are in a day's channel and records its appearance for Matrix, as for any project;
- archives the channel when the day's project closes or is deleted, and unarchives it if it reopens.

`projectChannelName` still gives a day's project `project-YYYY-MM-DD`, which is the name dailylinear asks for.

## API

- `Sync`: `adopt(adoption)` for autolinear's hand-over (see [autolinear's issues](#autolinears-issues)), and `run(kind, payload)` for the jobs `linear` (a webhook body: Issue, Comment or Project), `adopted` (the rest of a hand-over), `answered` (Hermes's finished turn, checked for a command), `command` (a command for Autolinear, from Hermes's message or Leon's `/autolinear`), `stuck` (a turn Hermes took up hasn't ended), `turns` (the channels where Hermes's gateway runs a turn), `muse-answer` (a Muse answer no Hermes turn will read), `slack` (a message, Hermes's command to Autolinear included, or a 👀, ✅ or ❌ `reaction_added` event), `project` (a delayed look at a new project), `timer` (an issue's time came), `tick` and `backfill`, plus `syncIssue(issue, "live" | "quiet")` and `syncProject(project)`.
- `Store`: issue ↔ channel, project ↔ channel and comment ↔ message mappings, a Slack user name cache, and the durable job queue (dedupe for 3 days, backoff, `dead` after six attempts, optional delay), whose delayed jobs are also the timers (`setTimer`, `timer`), plus the `fired` record of what happened once (due times announced, Hermes's commands and Autolinear's reminders) and the `acks` record of the status each issue had before Hermes's 👀 moved it. It runs over any `Sql`: a Durable Object's `storage.sql`, or `node:sqlite` in tests.
- `LinearClient`: Linear's GraphQL API with a personal API key, including `createProjectChannel` above, `team` and `createIssue` (with an ID the caller picks) for autolinear, `projectsNamed`, `projectStatuses`, `createProject` (with an ID the caller picks) and `updateProject` for dailylinear, and `projectsInStatus`, `projectText` (a project with its summary and body) and `openIssuesInProjects` for Routine and Watcher projects.
- `Routines` (with `RoutinesDeps`): runs a `routines` job (see [Routine and Watcher projects](#routine-and-watcher-projects)), plus `routineLink`, `withRoutineLink`, `isRoutine`, `routineName`, `routineProjectText` and `readSnapshot`.
- `botClient`: the Slack Web API with a bot token. `Sidebar` covers the sections above, and `tolerate` treats the listed Slack errors as success.
- `readTurns` and `readMuseAnswer`: check the hermes22muse relay's reports before autolinear's Worker queues them.
- `verifySlack` and `verifyLinear`: request signatures with a five-minute window.
- autolinear's IDs: `AUTOLINEAR_ID_PREFIX`, `autolinearIssueId`, `isAutolinearIssue`.
- Format helpers: `linearToSlack`, `slackToLinear`, `intakeTitle`, `excerptQuote` (from `#sync`), `channelName`, `projectChannelName`, `projectDay`, `localDay`, `channelNumber` and `channelTopic`, and for times `metaInstant`, `hasTime`, `zonedIso` (RFC 3339 in Toronto's offset), `withDay` (a time moved to another day), `addDays` and `localLabel`.
- Autolinear's commands: `commandLine`, `parseCommand`, `matchStatus`, `commandUsage`, `COMMAND_KEYS` (from `#command`).
- `loadConfig(env)`: settings from the Worker's vars (the `#slack22linear` items of the root `.env.schema`). `SLACK_LEON_USER_ID` and `SLACK_HERMES_USER_ID` are required: they have no built-in default. `AUTOLINEAR_BOT_USER_ID` names Autolinear's bot; without it, only a plain `@Autolinear` line is a command and no reminders are posted. `ROUTINE_PROJECT_STATUS`, `WATCHER_PROJECT_STATUS` and `HERMES_STATE` name the Routine and Watcher project statuses and the issue status that asks Hermes (Routine, Watcher, Awaiting Hermes).
